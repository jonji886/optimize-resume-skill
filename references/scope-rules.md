# 职责 Scope 校准

选择 bullet 动词时阅读。`scripts/validate_claims.py` 的 `SCOPE_INFLATION` /
`SCOPE_OVERREACH` / `SCOPE_UNVERIFIABLE` 检查与本文档一致。

## 层级与用词

| 层级 | 含义 | 常用表达 | 值 |
|---|---|---|---|
| `owner` | 独自设计或完成，从 0 到 1 | 独立设计、独立搭建、独立完成、全权负责 | 3 |
| `lead` | 跨团队推进并承担主要结果 | 主导、牵头、统筹、带领团队、端到端负责 | 2 |
| `core_execution` | 承担关键模块 | 负责、承担、实现、集成、落地、定位、编写、开发、设计、搭建、推进、重构、调优 | 1 |
| `support` | 提供局部或辅助工作 | 支持、协助、跟进、维护、配合、参与、辅助 | 0 |

「上线」「交付」等纯活动词不体现 scope，不计入判定。

- fact 的 `scope` 记录真实层级，claim 使用的动词级别不得高于它。
- 「主导」整份简历通常不超过 3 次，但以 fact 为准。
- 最终简历不展示 scope 标签。
- 「负责」「参与」「优化」「推动」并非绝对禁用；只有缺少具体对象、动作和结果时才替换。

## 升级判定

| evidence scope | claim 动词 | 结果 |
|---|---|---|
| `support` | `core_execution` | 警告 `SCOPE_OVERREACH`，建议改回支持性动词 |
| `support` | `lead` / `owner` | 错误 `SCOPE_INFLATION` |
| `core_execution` | `lead` / `owner` | 错误 `SCOPE_INFLATION` |
| `lead` | `owner` | 警告 `SCOPE_OVERREACH` |
| 未声明 | `lead` / `owner` | 警告 `SCOPE_UNVERIFIABLE`，先确认再写 |

降级（lead → support 表述）不会报错，但会让面试官低估候选人，需按事实写回。

## 什么时候必须回问用户

- fact 的 scope 是 `unspecified`，却需要用到「主导 / 独立负责」这类表达；
- 同一段经历里既有个人交付又有跨团队协调，无法判断边界；
- JD 的职级明显高于简历现有 scope，且事实无法支撑。

回问时只问层级本身，例如：
「XX 项目中接口方案是你独立定的，还是和架构师一起定的？」

## 常见升级错误

| 原始事实 | 错误表达 | 可信表达 |
|---|---|---|
| 参与项目实施 | 主导项目实施 | 参与项目实施，承担 XX 模块的联调与上线验证 |
| 支持客户问题处理 | 负责客户问题处理全流程 | 支持客户问题处理，梳理现象、影响范围与优先级 |
| 维护订单模块 | 主导订单平台建设 | 维护订单模块，定位并修复 3 个高优先级问题 |
| 协助需求沟通 | 独立完成需求调研 | 协助需求沟通，整理客户反馈与技术约束 |
| 按模板实施方案 | 独立设计整体架构 | 在既定方案框架下完成 XX 模块的方案细化与落地 |

## scope 与「可迁移」的组合

底层能力相近但场景不同的事实，即使在原场景中是 `owner`，迁移到目标岗位语境时
仍然只能作为可迁移能力表达，不得直接声称目标场景的经验。

- 错误：`具备支付 API 项目经验`
- 正确：`具备复杂 OpenAPI 接入与系统集成经验，可迁移至支付 API 场景`

对应的 claim 需显式声明 `claim_type: transferable`。

# JD 拆解、证据映射与职业风险诊断

Intake 阶段阅读。产出 JD Evidence Map，供内容筛选使用。

## 1. JD 拆解

提取并写入 fact store 的 `jd` 段：

- 3 个核心硬技能（写入 `jd.core_requirements`）；
- 2 个可行为验证的软素质；
- 职级与 scope 预期（写入 `jd.seniority`）；
- 行业标签（写入 `jd.industry`）；
- 明确的必备项与加分项；
- 需要在 ATS 中检索的真实技术 / 产品 / 职责名词（写入 `jd.ats_keywords`）。

`core_requirements` 与 `ats_keywords` 保持精简，只放真正要校验的词条。
`validate_claims.py` 会检查：有事实支持却未体现 → 告警或报错；出现却无事实支持 → 告警。

## 2. 证据映射

为每一项 JD 要求寻找事实证据，逐条标记：

| 标记 | 含义 | 可以怎么写 |
|---|---|---|
| 直接匹配 | 同类岗位、客户或项目中做过 | 正常写，可进入个人优势 |
| 可迁移 | 底层能力相近，场景不同 | 写清原场景 + 「可迁移至…」，`claim_type: transferable` |
| 无证据 | 没有事实支持 | **不写成已具备**；在交付说明中列为缺口 |

把「直接匹配」的证据回写到对应 fact 的 `jd_requirements`，这样覆盖度检查才有依据。
「无证据」不进入 fact store 的 confirmed，必要时记为 `unknown`。

## 3. 职责语义对齐

证据映射与表达映射必须分开检查：简历中存在相关事实，不等于该条经历已经用
目标岗位的语言呈现。

逐条检查标题、动作、对象和结果是否对应 JD 的职责动词与能力要求：

- 若原始表述偏「技术支持」，但事实包含需求澄清、业务流程拆解、影响判断、
  研发协同或上线验证，应改写为目标岗位可识别的「需求分析、问题拆解、方案落地」；
- 改写只能重新组织已确认的动作和结果，不得把技术支持包装成客户成功、
  客户 AI 场景挖掘、项目主导或商业结果；
- 删除与目标岗位无关的渠道性描述（工单、微信群）时，要保留其背后的客户对象、
  问题类型、判断过程和交付结果；
- 对 JD 前 3 个核心要求逐条做「证据 + 语义」双检。

示例（事实支持面向客户 IT/业务团队梳理问题、判断影响范围并推进上线验证）：

- 原表述：`- **客户问题受理**：通过工单、微信群响应客户反馈，梳理问题现象、影响范围和优先级`
- 目标岗位表述：`- **需求与问题拆解**：面向客户 IT/业务团队梳理问题现象、影响范围、优先级和业务流程，将复杂问题转化为明确的排查路径、研发需求和上线验证项`

## 4. 职业风险扫描

首次优化时检查，结论写入诊断。称其为「需解释项」，避免把正常转型直接定义成硬伤。

| 项目 | 参考阈值 | 处理方式 |
|---|---|---|
| 任职稳定性 | 连续 3 段平均少于 1.5 年 | 询问项目制、业务调整等真实背景 |
| 空窗期 | 最近 5 年内超过 6 个月 | 询问真实经历；未确认不得解释 |
| 职业路径 | 岗位方向发生明显变化 | 说明能力迁移，不直接判定为降级 |
| 行业连续性 | 3 年内切换 2 个以上不相关行业 | 提炼共通能力并弱化无关经历 |
| 学历与年限 | 不满足 JD 硬性条件 | 明确风险，不通过文案掩盖 |

工作年限按实际任职月份计算，不用「当前年份 − 毕业年份」替代。

## 5. 需要向用户确认时

只有出现 `fact-boundaries.md` 中的 Critical Missing Information 才阻断。
其余缺口按 claim-level gate 处理：先出简历，再把未覆盖的 JD 要求列成待确认项。

提问只覆盖高价值缺口，最多 5 个，并说明每个问题是在补 ATS 证据、
补 scope 事实，还是澄清职业风险。
